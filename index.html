Problem & Decision · Local Stamp

사용자 역할 검사와 데이터 접근 검사 분리

요구사항
사용자 역할을 확인하고 관리자 담당 지역과 계정 상태에 따라 접근을 제한
각 API별 검사
각 기능에서 역할을 직접 검사하면 여러 API에 같은 검사 코드가 반복됨
스프링 필터 검사
요청 경로별 역할 검사를 필터 한곳에서 공통으로 적용
결정
공통 역할 검사는 필터에 모으고 담당 지역과 계정 상태는 각 기능에서 DB로 확인
선택 과정

여러 API에서 반복되는 역할 검사 코드를 줄이기 위해 Spring Security 필터에 검사를 모았습니다. 권한이 없는 요청은 서비스 로직을 호출하기 전에 거부하므로 불필요한 서비스 호출도 줄일 수 있다고 판단했습니다.

담당 지역은 토큰에 담고 토큰 발급·재발급 때 조회하는 방식도 고려했습니다. 다만 운영 데이터가 없어 토큰 재발급 요청 수와 API 호출 수를 바탕으로 실제 DB 조회 감소 폭을 비교하기 어려웠습니다.

효과가 확인되지 않은 상태에서 기존 지역 검사 API들을 수정하고 재검증하는 비용이 커 전환하지 않았습니다. 따라서 담당 지역과 계정 상태는 각 기능에서 DB로 확인하는 방식을 유지했습니다.

Implementation & Result · Local Stamp
IMPLEMENTATION 01
  • 로그인과 토큰 재발급 시 유효기간이 15분인 Access Token에 사용자 역할을 담았습니다.
  • Spring Security 필터는 이 역할로 요청 경로에 접근할 수 있는지 확인합니다.
IMPLEMENTATION 02
  • 기능 실행 전에는 DB에서 관리자 담당 지역과 계정 상태를 조회했습니다.
  • 담당 지역이 다르거나 비활성 계정이면 요청을 거부하도록 했습니다.
VERIFICATION
  • 토큰에 담긴 역할과 경로별 접근 허용 여부를 단위 테스트와 MockMvc 기반 테스트로 확인했습니다.
  • 인증 실패 401과 권한 부족 403 응답도 확인했습니다.
  • 담당 지역·계정 상태에 따른 접근 제한을 테스트했습니다.
TRADE-OFF
  • 관리자 역할을 변경해도 이미 발급된 토큰에는 기존 역할이 최대 15분간 남습니다.
  • 반면 담당 지역과 계정 상태는 요청마다 DB에서 조회하므로 변경된 값이 다음 요청부터 반영됩니다.
결과

역할 검사는 Spring Security 필터에 모아 공통으로 적용했습니다. 담당 지역과 계정 상태는 각 기능에서 DB로 확인해 접근 가능 여부를 판단했습니다.

다만 로그인 시도 횟수 제한을 적용하지 못한 점은 아쉬움으로 남았습니다. 추후에는 계정별·IP별 로그인 시도 횟수를 제한해 비밀번호를 반복 대입하는 Brute Force와 유출된 계정 정보를 재사용하는 Credential Stuffing에 대한 방어를 보완하려 합니다.

Problem & Decision · gifbottary

WebSocket/STOMP에 Redis Pub/Sub을 추가한 이유

기존 구현
WebSocket/STOMP와 Spring의 Simple Broker로 실시간 채팅 전달
확장 한계
Simple Broker는 다른 서버에 연결된 사용자에게 메시지를 전달하지 못함
Redis 추가
각 서버가 같은 Redis 채널을 구독해 메시지를 받은 뒤 연결된 사용자에게 전달
남은 문제
Pub/Sub만으로는 접속이 끊긴 동안 받지 못한 메시지를 다시 조회할 수 없음
선택 과정

처음에는 WebSocket/STOMP와 Spring의 Simple Broker로 채팅을 구현했습니다. 이후 여러 서버에서도 대화할 수 있는지 확인해 보라는 피드백을 받았습니다. 구조를 살펴보니 Simple Broker는 해당 서버에 연결된 사용자에게만 메시지를 전달했습니다.

이 문제를 해결하기 위해 기존 연결은 유지하고 Redis Pub/Sub을 추가했습니다. 각 서버가 같은 채널을 구독한 뒤 연결된 사용자에게 메시지를 전달하도록 했습니다. 다만 Pub/Sub에는 대화 기록이 남지 않습니다. 그래서 메시지를 MySQL에 먼저 저장하고 재접속 시 API로 이력을 조회하도록 했습니다.

Implementation & Result · gifbottary
IMPLEMENTATION 01
  • 메시지 전송 요청에서 채팅방 참여자 여부와 입력값을 확인했습니다.
  • 이후 Redis로 발행하기 전에 메시지를 MySQL에 저장했습니다.
IMPLEMENTATION 02
  • MySQL에 저장한 메시지를 Redis 채널에 발행했습니다.
  • 각 서버는 구독한 메시지를 연결된 사용자에게 STOMP로 전달했습니다.
  • 재접속한 사용자는 API로 대화 이력을 조회할 수 있습니다.
VERIFICATION
  • 단위 테스트로 Redis 발행 호출을 확인했습니다.
  • 서버 간 전달은 판매자와 구매자를 서로 다른 로컬 서버에 연결해 직접 확인했습니다.
TRADE-OFF
  • MySQL 저장 후 Redis 발행이 실패하면 실시간으로 메시지를 받지 못할 수 있습니다.
  • 다만 DB에 저장된 대화는 재접속 후 조회할 수 있습니다.
결과

로컬 서버 두 대에서 서로 다른 서버에 접속한 판매자와 구매자가 메시지를 주고받는 것을 확인했습니다.

다만 Redis 발행에 실패한 메시지는 자동으로 재전송되지 않습니다. 사용자는 재접속 후 대화 이력을 조회해야 DB에 저장된 메시지를 확인할 수 있습니다. 추후에는 발행 실패 시 재시도할 수 있도록 Outbox 패턴을 적용해 보려고 합니다.

Problem & Decision · Checkout System

외부 결제 조회와 DB 트랜잭션 분리

요구사항
외부 결제 결과를 확인한 뒤 내부 결제 상태와 재고에 반영
트랜잭션 범위
외부 응답을 기다리는 구간은 제외하고 함께 반영할 DB 변경을 하나로 묶음
중복 위험
재요청이나 웹훅으로 같은 실패 결과가 들어오면 재고 복구가 반복될 수 있음
결정
외부 조회 후 별도 서비스의 트랜잭션에서 결과를 반영하고 실패 처리는 PENDING 상태로 제한
선택 과정

DB 조회와 외부 API 호출을 하나의 트랜잭션으로 묶으면 외부 응답을 기다리는 동안에도 확보한 DB 연결을 점유할 수 있습니다. 외부 응답이 느려지고 동시 요청이 늘면 다른 요청이 DB 연결을 기다리는 문제가 생길 수 있다고 판단했습니다. 따라서 외부 조회는 트랜잭션 밖에서 수행하고 결과를 반영하는 DB 작업만 별도 서비스의 트랜잭션으로 묶었습니다.

결제 실패 시 결제 상태 변경과 재고 복구를 하나의 트랜잭션으로 묶었습니다. 한쪽만 반영되는 일을 막기 위해 두 작업이 함께 반영되거나 함께 롤백되도록 했습니다.

Implementation & Result · Checkout System
IMPLEMENTATION 01
  • DB 트랜잭션 밖에서 외부 결제 정보를 조회했습니다.
  • 결제 ID가 다르면 오류를 반환했습니다.
  • 결제 완료 상태와 주문 금액이 모두 일치하면 성공 처리하고 그 외에는 실패 처리로 분기했습니다.
IMPLEMENTATION 02
  • PENDING 상태에서만 실패 처리와 재고 복구를 실행했습니다.
  • 두 작업은 하나의 트랜잭션으로 묶었습니다.
  • 동시 변경은 JPA 낙관적 락(@Version)으로 감지하도록 했습니다.
VERIFICATION
  • HTML 화면에서 결제를 진행하고 Postman으로 결제 성공·실패 API의 응답을 확인했습니다.
  • MySQL에서도 저장된 값을 확인했습니다.
TRADE-OFF
  • 외부 API 응답 대기를 트랜잭션에서 제외해 DB 연결을 오래 점유할 위험을 줄였습니다.
  • 대신 외부 조회와 DB 반영이 나뉘므로 조회 성공 후 DB 반영에 실패한 경우의 재처리 흐름을 별도로 관리해야 합니다.
결과

외부 결제 결과에 따라 내부 결제 상태를 반영하고 실패한 주문의 재고를 복구하는 흐름을 구현했습니다. Postman에서 결제 성공·실패 API의 응답을 확인했고 MySQL에서도 저장된 값을 확인했습니다.

이 과정에서 함께 반영돼야 하는 데이터 변경을 기준으로 트랜잭션 범위를 정해야 한다는 점을 배웠습니다.
